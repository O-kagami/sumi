# 省メモリ化とRustの判断

更新：2026-11-25（Sumiへの移行）  
状態：コード調査に基づく計画。現時点の使用MB数・削減率は未測定。

## 1. 方針

初版は既存C++変換エンジン・TSF・候補描画を活用し、メモリを使っている部品と寿命を測る。Rustの部分採用は同条件の比較試作で決める。

Rustの所有権は安全なメモリ管理に役立つが、C++から言語だけを変えて辞書やモデルの容量が減るとは仮定しない。WinUI設定アプリをC++/WinRTで作ることによる通常入力中の削減効果も、根拠なく主張しない。[資料R1](references.md#performance)

## 2. 基準を揃える

1. 比較対象の配布版を記録。
2. 固定コミットの未改変版をビルド。
3. 同コミットの改変版を同じ辞書・モデル・履歴・入力文章・電源モードで比較。

Mac互換仕様を崩して処理を省略しない。AI OFFの節約は機能選択による差として分ける。インストーラー容量、ディスク上のモデル容量、私有コミット量、物理RAMを混同しない。

## 3. 測定

ARM64・16GBクラスのWindows実機を中心に、x64でも確認する。

| 状態 | 測定する点 |
| --- | --- |
| サインイン直後・IME未使用 | 自動起動、ベース常駐 |
| 通常ライブ変換・AI OFF | 変換と候補UIの基準 |
| AI ONの初回・連続入力 | 読込みピーク、定常使用量、応答 |
| 候補選択・文節編集の反復 | UI資源、ハンドル、学習・キャッシュ |
| 複数アプリ | TSFの増分、セッションの重複 |
| アイドルと再開 | 解放効果、cold start、入力の引っかかり |
| WinUI設定の開閉 | 起動中の追加分、終了後の残存 |
| スリープ復帰・長時間反復 | 状態復元、増加傾向 |

Private Bytes/Commit、Working Set、Private Working Set、共有ページ、CPU、起床回数、ハンドル数、入力・候補・AI応答のp50/p95/p99を記録する。

ホストアプリの全メモリをIMEへ加算しない。共有ページを二重計上しない。VMMapとWPR/WPAの対応状況を確認して使用する。working setを一時的に追い出しただけの減少を恒常的な最適化と評価しない。[資料R2〜R4](references.md#performance)

最初の測定で、メモリの削減目標、p95/p99の上限、AI再開時間、長時間の私有メモリ増加の許容値を数値化し、後続の採否基準にする。

## 4. 優先順

1. 基準Macで不要な自動予測生成・キャッシュ出力を止める。
2. AI OFF時／一定時間未使用時のscorer・llamaの解放を検証。
3. cache serviceとprelaunchの必要性を調べる。
4. WinUI設定を閉じた後の終了、候補の描画資源、文字列等の重複を確認。
5. 辞書の埋込み／マップ経路と不要なコピーを調べる。
6. 変換品質を測りながらモデル・文脈長等を比較。
7. プロセス統合やRustでの制御部分の置換を比較。

現在のWindows scorerには要求時起動、推論スロット数1、グローバルRAM prompt cache無効化が既にある。既存の改善を新規の成果に数えない。[上流U8](references.md#upstream)

停止は自分が所有するプロセス・要求を対象にし、無関係なllamaプロセスを名前だけで終了しない。AI再起動中も通常のライブ変換を継続し、古い応答を別のセッションへ適用しない。

## 5. Rustの比較方法

C++で寿命管理等を改善した版と、同じ設計のRust試作を比較する。モデル変更、機能OFF、キャッシュ制限の効果を、言語の効果へまとめない。

部分移行候補はAIプロセスの起動・停止・要求管理や、独立した新規ロジック。TSFや変換エンジンの全面移植を、初版の必須条件にしない。

採用するのは、削減が再現し、入力遅延・再開時間が基準内で、Mac互換・学習・確定・取消に退行がなく、ARM64/x64と上流追従を保守できる場合。わずかな削減のために複雑さが大きく増える場合は見送る。
